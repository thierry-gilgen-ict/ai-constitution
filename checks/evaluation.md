# Evaluate a route before promoting it

Choose representative tasks from your actual work: one small edit, one implementation, one difficult bug, one review, and one research task. Use comparable inputs and verify results against observable acceptance criteria.

| Field | Record |
| --- | --- |
| Task and acceptance criteria | What must be correct |
| Client and model | Exact selector, settings, client version, availability |
| Instruction release | Version or Git commit |
| Quality | Passed criteria, regressions, material omissions |
| Time | Elapsed time, retries, human intervention |
| Cost | Actual reported usage; distinguish subscription limits from API charges |
| Capability needs | Tools, context, modalities, local hardware |
| Decision | Keep, promote, reject, or collect more evidence |

Use an agreed budget before paid evaluations. Keep private tasks and results outside this public repository. Publish sanitized summaries only with authorization. A small sample supports a local decision, not a universal leaderboard.

The initial route table is a useful starting point with source-linked model descriptions. It has not been validated by a comparative task benchmark. Retain the user's chosen model until changing it is part of the request.
